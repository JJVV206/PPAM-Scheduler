1. Que es y para que sirve

PPAM Scheduler es una aplicacion full-stack en Next.js para coordinar asignaciones semanales de predicacion publica con experiencias separadas para administradores y voluntarios.

Sirve para operar una semana real de punta a punta: preparar el calendario, asignar parejas, pedir confirmaciones, seguir respuestas y reaccionar a vacantes o rechazos desde la UI.

2. Contexto, origen y evolucion

La mejor evidencia del contexto funcional sale del README, del schema Prisma y de las rutas protegidas en `app/(protected)/admin` y `app/(protected)/volunteer`. El dominio de predicacion publica y coordinacion semanal se desprende de nombres de modelos, paginas y datos seed.

El repo muestra senales de haber pasado de un esqueleto MVP a un flujo operativo mas cerrado: hoy existen duplicacion de semana, enlaces directos de confirmacion, excepciones temporales de disponibilidad, active slots por punto y scripts mas robustos para la base local.

Por el lenguaje del dominio, el uso visible parece estar enfocado en coordinadores y voluntarios de predicacion publica. Eso esta fuertemente sugerido por el repo, aunque la politica exacta de uso por congregacion o region no esta documentada.

3. Como funciona en lenguaje simple

Un admin entra al workspace, crea o duplica una semana, arma asignaciones y las sigue desde planner, tablas y modales. Los voluntarios reciben solicitudes, responden desde portal o correo y el sistema recalcula estados, genera vacantes y ofrece candidatos de reemplazo segun disponibilidad y conflictos.

Dentro de una organizacion, esta herramienta encaja como sistema operativo semanal para un equipo pequeno que coordina turnos, coberturas y confirmaciones con trazabilidad minima.

Workspace admin

Reune dashboard, horario semanal, asignaciones, voluntarios, puntos, vacantes, notificaciones y configuracion.

Portal del voluntario

Expone inicio, mis asignaciones, vacantes compatibles, disponibilidad, notificaciones y perfil.

Motor operativo de asignaciones

Concentra reglas de estados, confirmaciones, doble booking, reemplazos y duplicacion de semanas.

Persistencia, notificaciones y setup local

Usa Prisma sobre PostgreSQL, logs de notificacion y scripts locales para levantar datos demo de forma reproducible.

4. Problemas que resuelve y beneficios

Problemas que ayuda a resolver

  • • Evita preparar semanas por fuera del sistema o depender de llamadas manuales a endpoints para completar flujos criticos.
  • • Reduce perdida de visibilidad sobre quien ya confirmo, quien rechazo y donde faltan posiciones por cubrir.
  • • Ayuda a proponer reemplazos compatibles usando disponibilidad recurrente, excepciones temporales y ausencia de conflicto horario.
  • • Disminuye errores operativos al concentrar estado, actividad y notificaciones en una sola base de datos.

Beneficios principales

  • • Permite operar una semana completa desde la interfaz principal del admin.
  • • Ofrece una experiencia clara para voluntarios con detalle, respuesta y disponibilidad actualizable.
  • • Deja evidencia minima util para QA, demos y handoff mediante timeline de actividad y NotificationLog.

5. Personas, equipos y operacion

Quienes suelen interactuar

  • • Coordinadores o admins responsables del horario semanal.
  • • Voluntarios que participan en las asignaciones y reemplazos.
  • • Desarrolladores que mantienen UI, reglas de negocio, autenticacion, datos y notificaciones.

Como se maneja o administra

  • • El admin administra semanas, puntos, vacantes y confirmaciones desde pantallas protegidas por rol.
  • • El entorno local se levanta con PostgreSQL en Docker, Prisma para schema y seed, y `next dev` para la app.
  • • Las variables `DATABASE_URL`, `NEXTAUTH_SECRET` y la configuracion SMTP controlan persistencia, sesion y envio de correos.

6. Ejemplos, analogias y casos sencillos

Ejemplo 1: rechazo y vacante

Si un voluntario rechaza, la asignacion cambia a `NEEDS_REPLACEMENT`, aparece en vacantes y el admin puede escoger un reemplazo sugerido.

Como una guardia medica donde el turno sigue existiendo aunque cambie la persona asignada.

Ejemplo 2: preparar una nueva semana

El coordinador puede clonar una semana anterior, navegar al nuevo rango y seguir ajustando parejas o puntos sin rehacer todo desde cero.

Como duplicar un calendario semanal y solo corregir los cambios de esta semana.

7. Errores comunes o confusiones

  • • No es solo un frontend: el mismo repo contiene handlers, servicios y Prisma como backend integrado.
  • • Una semana visible en el planner no equivale automaticamente a un `ScheduleWeek`; primero debe existir el registro de semana para poder asignar.
  • • El enlace directo de correo hoy usa `responseId` y resuelve el MVP, pero no sustituye automaticamente una estrategia de hardening para produccion.

8. Que debe saber una persona junior

  • • Empieza por README, luego `prisma/schema.prisma`, `services/assignment.service.ts` y las paginas de admin y volunteer.
  • • Entiende primero los modelos de dominio: semana, asignacion, voluntario, respuesta, punto y notificacion.
  • • Sigue un flujo real de negocio antes de cambiar codigo: crear semana, crear asignacion, confirmar, rechazar y cubrir vacante.
  • • Verifica siempre si una regla vive en UI o en `services/`; la logica importante esta mayormente del lado de servicio.
  • • Levanta la base con `npm run db:start`, `db:push` y `db:seed` antes de sacar conclusiones sobre rutas o datos vacios.

9. Glosario

Punto de predicacion

Lugar donde se agenda una o mas parejas en dias y franjas concretas.

Asignacion

Registro que combina fecha, horario, punto, numero de pareja, voluntarios y estado operativo.

Vacante

Asignacion incompleta o afectada por un rechazo que requiere reemplazo.

Disponibilidad temporal

Bloque excepcional de fechas donde un voluntario no debe aparecer como sugerencia.

NotificationLog

Bitacora donde queda registrado si una solicitud o recordatorio fue enviado o fallo.
