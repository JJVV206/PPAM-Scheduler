Stack actual

Aplicacion full stack con flujo transaccional para planeacion, respuesta y reemplazo.

La base actual combina Next.js App Router, React con TypeScript, Prisma y PostgreSQL, con autenticacion por credenciales y una capa de servicios que encapsula reglas de negocio, estados y notificaciones.

Next.js App Router React + TypeScript Prisma + PostgreSQL NextAuth Credentials TanStack Query Zod + React Hook Form

Criterio tecnico central

La arquitectura esta organizada para proteger tres cosas: integridad de asignaciones, control de estados y trazabilidad de lo que hace cada usuario durante la semana.

  • Sin doble asignacion en la misma fecha y franja
  • Estados recalculados segun respuestas y ventana de confirmacion
  • Actividad, notificaciones y disponibilidad persistidas

Dominio

Modelo de datos que sostiene la operacion

Usuarios y perfiles

  • User define identidad, credenciales y rol
  • VolunteerProfile guarda confiabilidad, preferencias y contadores
  • VolunteerAvailability y AvailabilityException modelan recurrencia y bloqueos

Planeacion

  • PreachingPoint y PreachingPointActiveSlot representan puntos y franjas activas
  • ScheduleWeek agrupa el marco semanal
  • Assignment y AssignmentVolunteer unen punto, horario, pareja y posicion

Ejecucion

  • AssignmentResponse guarda confirmacion o rechazo
  • NotificationLog deja rastro de solicitudes y recordatorios
  • AssignmentActivity actua como timeline operativo

Configuracion

  • AppSetting define anticipacion de confirmacion
  • Tambien define cadencia de recordatorios y canales habilitados
  • Permite modificar comportamiento sin tocar codigo

Flujos tecnicos

Como viajan las acciones por el sistema

Flujo 1

Crear o editar asignacion

  1. Admin usa planner o formulario de asignacion.
  2. La UI envia la peticion al endpoint de /api/assignments.
  3. Zod valida fecha, franja, punto y voluntarios.
  4. assignment.service revisa conflictos con assertNoVolunteerConflicts.
  5. Prisma crea o actualiza Assignment, posiciones y respuestas pendientes.
  6. El motor determineAssignmentStatus define si queda programada, pendiente o necesita reemplazo.

Flujo 2

Confirmar o rechazar

  1. Voluntario entra al portal o responde desde su flujo de confirmacion.
  2. La solicitud pega a /api/assignments/[id]/confirm o /decline.
  3. Los guards verifican sesion y rol VOLUNTEER.
  4. La respuesta se guarda en AssignmentResponse.
  5. Se registra AssignmentActivity con la accion recibida.
  6. Si confirma, se recalcula el estado; si rechaza, pasa a NEEDS_REPLACEMENT.

Flujo 3

Resolver vacantes y reemplazos

  1. Las vacantes salen de asignaciones incompletas o rechazadas.
  2. getOpenSlots identifica posiciones faltantes y urgencia.
  3. getAvailableVolunteersForSlot filtra por disponibilidad, conflictos y bloqueos temporales.
  4. El admin reasigna via /api/assignments/[id]/replace.
  5. La transaccion reemplaza posicion, recrea respuesta pendiente y registra actividad.
  6. El estado vuelve a evaluarse con la nueva composicion de la pareja.

Flujo 4

Actualizar disponibilidad

  1. El voluntario modifica su disponibilidad recurrente.
  2. La UI envia PUT /api/availability.
  3. La validacion acepta items recurrentes, bandera temporal y excepciones.
  4. availability.service reemplaza disponibilidad y bloqueos dentro de una transaccion.
  5. El perfil conserva una vista consistente para futuras sugerencias y chequeos.

Estado y reglas

Motor de decisiones de la asignacion

Entrada del motor

  • Fecha de la asignacion
  • Cantidad de voluntarios en la pareja
  • Respuestas actuales de cada voluntario
  • Dias de anticipacion configurados para confirmar

Salida del motor

  • NEEDS_REPLACEMENT si falta alguien o hay rechazo
  • CONFIRMED si ambos confirman
  • PENDING_CONFIRMATION si entro a ventana de confirmacion
  • SCHEDULED si aun no corresponde pedir respuesta
